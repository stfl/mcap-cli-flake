#+TITLE: mcap-cli-flake
#+AUTHOR: stfl

The [[https://github.com/foxglove/mcap][MCAP]] command-line tool, ~mcap~, packaged for Nix at v0.3.0 — the Rust
implementation.

nixpkgs carries ~mcap-cli~ at 0.0.62, the Go implementation that preceded the
rewrite. This flake stands in for it until the rewrite lands upstream; the
package expression here is written to be adopted into nixpkgs with the two edits
noted below and nothing more.

* Use it

Run it without installing:

#+begin_src sh
nix run github:stfl/mcap-cli-flake -- info recording.mcap
#+end_src

As a flake input, consumed through the overlay:

#+begin_src nix
{
  inputs = {
    nixpkgs.url = "github:NixOS/nixpkgs/nixos-unstable";

    mcap-cli-flake.url = "https://flakehub.com/f/stfl/mcap-cli/*";
    mcap-cli-flake.inputs.nixpkgs.follows = "nixpkgs";
  };

  outputs =
    { nixpkgs, mcap-cli-flake, ... }:
    {
      # nixpkgs.overlays = [ mcap-cli-flake.overlays.default ];
      # environment.systemPackages = [ pkgs.mcap-cli ];
    };
}
#+end_src

~overlays.default~ replaces the ~mcap-cli~ attribute nixpkgs defines, so anything
already referring to ~pkgs.mcap-cli~ picks this up.

Following the consumer's ~nixpkgs~ keeps one nixpkgs in the closure, at the cost
of building ~mcap~ locally rather than substituting a prebuilt one — nothing
pushes this package to a binary cache. Drop the ~follows~ line to substitute from
FlakeHub's cache instead and carry a second nixpkgs.

* Layout

| File                | Contents                                                             |
|---------------------+----------------------------------------------------------------------|
| ~package.nix~       | The derivation. nixpkgs house style, ~callPackage~-able, no flake-isms |
| ~flake.nix~         | Wraps ~package.nix~ into packages and an overlay for three systems     |
| ~ci/smoke-test.sh~  | Asserts a built result is the version ~package.nix~ declares           |

~package.nix~ takes nothing a nixpkgs tree would not already provide, so
upstreaming it is a copy into ~pkgs/by-name/mc/mcap-cli/~ rather than a rewrite.
Two edits belong in that copy:

- The ~maintainers~ list carries a literal attribute set for ~stfl~, who has no
  entry in ~maintainers/maintainer-list.nix~. Upstreaming adds the entry there
  and replaces the literal with the attribute name.
- Completions for bash, zsh and fish are generated by running the built binary,
  so a cross build runs it under an emulator. Where no emulator exists the three
  are skipped rather than failing the build.
- ~checkFlags~ skips eleven tests. They read fixtures stored as Git LFS objects,
  and a source tarball carries the pointer files rather than the payload
  ([[https://github.com/foxglove/mcap/issues/895][foxglove/mcap#895]]). The Go package skips the same class of test. The other
  338 run.

* Versions

~mcap --version~ reports three things:

#+begin_example
mcap 0.3.0 (21755244b) mcap-rust/0.25.0
#+end_example

The CLI version, the upstream commit, and the version of the ~mcap~ library crate
it was built against. The commit reaches the build through ~.gitattributes~
~export-subst~, which the GitHub source tarball expands — so it identifies the
release even though no ~.git~ directory exists at build time.

* Maintenance

Two scheduled jobs, deliberately separate so a red run says which axis moved:

| Workflow              | Bumps                          | A failure means                          |
|-----------------------+--------------------------------+------------------------------------------|
| ~update-package.yml~  | Upstream release, both hashes  | An upstream release this packaging must catch up with |
| ~update-lock.yml~     | The pinned nixpkgs             | rustc or dependency churn, usually self-resolving |

Each builds and smoke-tests before it pushes. A push made with ~GITHUB_TOKEN~
does not trigger ~on: push~ workflows, so a bump that verified nothing would sit
on ~main~ unchecked; verifying in the bump job itself is what keeps that from
happening.

CI covers x86_64-linux only. ~nix flake check --all-systems~ evaluates all three
systems ~meta.platforms~ claims, but only x86_64-linux is built and run. ofborg
is the gate that actually builds the others, at nixpkgs PR time.
